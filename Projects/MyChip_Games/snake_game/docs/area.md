# 면적 리포트 (ETRI 0.5um, 실측)

> **정정 이력**: 첫 판에서 "84핀 프레임을 쓰면 된다"고 적었으나 이는 틀렸습니다.
> 2026년 3차 내 칩 제작 서비스 공고 기준으로 **패키지 칩은 `MPW_PAD_28pin`
> 표준 배치만 가능**하고, 그보다 크게 설계하면 사전 협의 후 **bare die만**
> 제공됩니다. 또 utilization을 60%로 가정했으나 실제 테이프아웃 결과는
> 82.3% 였습니다. 아래는 모두 실측으로 다시 계산한 값입니다.

## 1. 면적 예산 — 어디서 나온 숫자인가

### 1-1. 코어 창: 1018 x 1018 um

DK 안의 실제 테이프아웃 결과물
(`Projects/RTL/pong_pt1/ETRI050_MyChip_MPW/pong_pt1_MPW2025_STD-II.tar.gz`)의
chip_top 레이아웃을 직접 측정했습니다. (lambda = 0.30um, magic 내부 단위 = 0.01um)

| 레이어 | 범위 | 크기 |
|---|---|---|
| `pong_pt1_Pad.mag` (패드링) | 91.5 ~ 1808.5 um | 1717 x 1717 um |
| `pong_pt1_Pin_Route.mag` (핀 라우팅 링) | **441.0 ~ 1459.0 um** | **1018 x 1018 um** |

핀 라우팅 링 안쪽이 코어가 쓸 수 있는 전부입니다.
**1018 x 1018 um = 1.036 mm²**, 공고문의 "GPIO 사용시 설계 면적 ~1.0mm x 1.0mm"와
일치합니다.

### 1-2. Utilization: 82.3%

같은 테이프아웃의 라우팅 완료 DEF (`pong_pt1.def`)에서:

```
DIEAREA (0,-600) (86400,83700)   ->  864.0 x 843.0 um = 0.7284 mm2
COMPONENTS 2065  ->  실제 셀 1017개 + FILL 1048개
실제 셀 면적 합 (LEF SIZE 기준)  =  0.5997 mm2
utilisation = 0.5997 / 0.7284   =  82.3 %
```

qflow(graywolf `initial_density = 0.85` + qrouter, 3-metal)의 실제 달성치입니다.

### 1-3. 따라서 예산

```
코어 창      1.036 mm2
x 82.3%   =  0.853 mm2 의 표준셀
          =  약 1974 GE  (GE = NAND2X1 면적 432 um2 기준)
```

## 2. 현재 설계

측정: yosys 0.33 → `khu_etri05_stdcells.lib` 매핑 → LEF `SIZE` 실측값으로 합산.
재현: `cd syn && python3 area.py`, `python3 modarea.py`

| 설정 | 셀 | FF | 셀 면적 | 코어 | 예산 대비 |
|---|---|---|---|---|---|
| 2x2 px, MAXLEN 48, 점수+텍스트 | 2876 | 422 | 1.776 mm² | 2.16 mm² | **2.08배** |
| 2x2 px, MAXLEN 48, 문자 제외 | 2650 | 417 | 1.655 mm² | 2.01 mm² | 1.94배 |
| 4x4 px, MAXLEN 32, 문자 제외 | 2404 | 375 | 1.499 mm² | 1.82 mm² | 1.76배 |
| 8x8 px, MAXLEN 16, 문자 제외 | 2132 | 330 | 1.328 mm² | 1.61 mm² | **1.56배** |

**가장 많이 줄인 설정조차 28핀 예산의 1.56배입니다.**

"MCU 없이"의 대가가 이만큼입니다.

## 3. 적용한 최적화

| 항목 | 전 | 후 |
|---|---|---|
| 코어 전체를 동기 리셋으로 | DFFSR(72x36um) 304개 | 0개. 3.09 → 2.77 mm² |
| **몸통을 좌표 큐 → 방향 큐로** | 좌표 11bit x 48 = 528 FF, 3331 GE | 방향 2bit x 48 = 96 FF, **1078 GE** |
| pixel_gen의 벽/먹이 계산 공유 | 픽셀 행 8개마다 비교기 | 상수 마스크 + 비교기 1개 공유 |
| 카운터 폭을 파라미터에서 계산 | 고정 16bit | `$clog2` |

방향 큐 전환이 결정적이었습니다. 뱀은 경로이므로 마디마다 좌표를 들고 있을
필요가 없고, 머리 위치 + 각 걸음의 방향 2비트만 있으면 머리에서 거꾸로 걸어가며
모든 마디를 복원할 수 있습니다. 스캔 회전에 맞춰 walker가 한 걸음씩 되짚으므로
렌더링/자기충돌/먹이배치는 전과 똑같이 동작합니다.

부수 효과로 **그리드 해상도와 뱀 길이가 거의 공짜**가 되었습니다
(2x2 px/MAXLEN 48 = 1.78 mm², 8x8 px/MAXLEN 16 = 1.33 mm²).
줄여야 할 것은 이제 게임판이 아니라 제어 로직입니다.

## 4. 남은 격차와 선택지

예산 1974 GE, 현재 4518 GE. 기능을 건드리지 않는 최적화로 짜낼 수 있는 것:

| 항목 | 예상 절감 |
|---|---|
| init 시퀀스를 필수 명령 11바이트로 축소 (나머지는 SSD1315 전원인가 기본값) | ~200 GE |
| `oled_ctrl` 의 `pix_x`/`pix_page`/`i2c_din` 중복 레지스터 제거 | ~55 GE |
| `eaten` 8→5bit, `food_try` 6→3bit, 고정 속도 | ~100 GE |
| debounce 3샘플 → 2샘플 | ~50 GE |
| lfsr16 → lfsr11 | ~20 GE |
| 점수/폰트 완전 제거 | ~390 GE |
| 8x8 px 셀 + MAXLEN 16 | ~800 GE |

전부 적용해도 약 2900 GE = 1.25 mm² 셀 = **1.5 mm² 코어**, 여전히 예산의 1.45배
입니다. 즉 **현 구조로는 28핀 패키지 칩에 들어가지 않습니다.**

부분 갱신(바뀐 칸만 다시 그리기) 구조로 바꿔도 절감폭은 300 GE 정도입니다.
면적이 렌더링이 아니라 제어 로직에 있기 때문입니다.
