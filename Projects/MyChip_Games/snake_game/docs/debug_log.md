# 디버깅 기록

SNAKE 칩을 만들면서 나온 버그 여섯 개와 분석 오류 두 개의 기록입니다.
각각 증상 → 어떻게 찾았나 → 원인 → 수정 → 재발 방지 순으로 적었습니다.

여덟 건 중 일곱 건은 제가 만든 실수입니다. 다시 볼 때 쓸모 있는 부분은 원인보다
**어떤 방법이 그것을 잡아냈는가** 쪽이라, 마지막에 그것만 따로 정리했습니다.

| # | 버그 | 발견 시점 | 잡아낸 방법 |
|---|---|---|---|
| 1 | I2C START 조건이 만들어지지 않음 | RTL 시뮬 첫 실행 | 2모듈 격리 + 신호 전이 출력 |
| 2 | 초기 몸통이 같은 칸에 두 번 기록 | RTL 시뮬 | 내부 레지스터 덤프 |
| 3 | 시프트 폭 잘림으로 셀이 엉뚱한 줄에 | RTL 시뮬 | 지향적 단위 테스트 |
| 4 | 테두리가 반만 그려짐 | 프레임 캡처 | ASCII 아트 덤프 |
| 5 | Zybo 조이스틱 핀 4개 오배정 | 합성 전 | 공식 XDC 대조 |
| 6 | 먹이가 벽 밑에 배치되어 안 보임 | **실제 보드** | 수열 전수 분석 |
| 7 | 면적 추정이 두 번 틀림 | 검토 중 | 실제 테이프아웃으로 캘리브레이션 |
| 8 | 패드 프레임 선택 오판 | 공고문 확인 | 1차 자료 확인 |

## 1. I2C START 조건이 만들어지지 않음

**증상** — 패널이 응답하지 않음. `oled_ctrl` 이 `T_RESLO → T_ADDR → NACK →
T_RESLO` 를 무한 반복. 시뮬레이션 모델의 `disp_on` 이 계속 0.

**어떻게 찾았나** — 전체 시스템 시뮬은 상태가 너무 많아 원인이 안 보였습니다.
`i2c_master` 와 SSD1315 모델 **둘만** 남긴 20줄짜리 테스트벤치를 만들고,
SCL/SDA가 바뀔 때마다 마스터 상태와 슬레이브 상태를 같이 찍었습니다.

```
     0 scl=1 sda=1  mst=0 ...
  6000 scl=0 sda=0  mst=3 ...   ← 두 신호가 같은 시각에 함께 떨어짐
```

START는 "SCL이 High인 동안 SDA가 떨어지는 것"인데 둘이 같이 떨어지면 START가
아닙니다. 슬레이브의 `in_xfer` 가 0으로 남아 있는 것과 정확히 일치했습니다.

**원인** — START 시퀀스가 두 상태뿐이었고 그중 하나가 이랬습니다.

```verilog
ST_STARTB: begin
    sda_r <= 1'b0;
    if (qtick) begin
        scl_r <= 1'b0;      // 같은 사이클에 SCL도 내림
        st    <= ST_BIT;
    end
end
```

quarter-bit 분주비 `DIV` 가 2 이상이면 `sda_r <= 0` 이 먼저 적용되고 `qtick` 은
나중에 와서 우연히 동작합니다. 시뮬레이션 속도를 위해 SCL을 높였더니 `DIV=1`
이 되면서 두 대입이 같은 사이클에 겹쳤습니다. **느리게 돌리면 숨는 버그**였습니다.

**수정** — START를 quarter-bit 네 단계로 쪼개서 두 신호가 절대 같은 사이클에
움직이지 않게 했습니다.

```
ST_STARTA  SDA 놓음 (SCL은 아직 Low)
ST_STARTB  SCL 놓음
ST_STARTC  SDA 내림  ← 여기가 START
ST_STARTD  SCL 내림
```

STOP도 같은 이유로 세 단계로 두었습니다. 이렇게 하면 반복 START에서 SDA와
SCL이 동시에 상승해 STOP처럼 보이는 문제도 함께 사라집니다.

**재발 방지** — 시뮬레이션을 `DIV=1` (가장 빡빡한 조건)로 돌립니다. 실칩은
`DIV=16` 이라 여유가 훨씬 큽니다.

## 2. 초기 몸통이 같은 칸에 두 번 기록

**증상** — 게임 시작 직후 `len=3` 인데 화면의 뱀은 2칸으로 보이고, 머리 위치가
기대값보다 1칸 왼쪽.

**어떻게 찾았나** — 게임 스텝마다 머리/길이/방향을 찍는 트레이스를 넣었더니
첫 스텝의 머리가 예상(31)이 아니라 30이었습니다. 몸통 레지스터를 직접 덤프해
보니 두 칸이 같은 좌표였습니다.

**원인** — `game_ctrl` 의 출력은 전부 레지스터입니다. 그래서 `body_move` 를 올린
사이클과 `snake_body` 가 실제로 움직이는 사이클이 **한 클럭 어긋납니다.**
빌드 루프가 그걸 무시하고 매 사이클 `head` 를 읽었습니다.

```verilog
S_BUILD: body_pos <= {hy, hx + 1'b1};   // head는 아직 갱신 전 → 같은 값 두 번
```

**수정** — `head` 를 되읽지 않고 `body_pos` 자체를 전진시켰습니다. 좌표 패킹에서
x가 하위 비트라 `+1` 이 곧 "오른쪽 한 칸" 입니다.

```verilog
S_BUILD: body_pos <= body_pos + 11'd1;
```

이 문제는 나중에 위치 연산을 통째로 `snake_body` 로 옮기면서 구조적으로
사라졌습니다 — 지금 `game_ctrl` 에는 위치 레지스터가 없습니다.

## 3. 시프트 폭 잘림 — 가장 미묘했던 것

**증상** — 뱀 몸통 일부가 화면에서 빠지고, 대신 엉뚱한 자리에 칸이 하나 켜짐.
몸통 레지스터를 덤프하면 내용은 **정확했습니다.** 즉 저장은 맞는데 그림이 틀림.

**어떻게 찾았나** — 시스템 시뮬은 한 번 돌리는 데 2분이라 반복이 느렸습니다.
`snake_body` + `pixel_gen` 만 떼어낸 **지향적 단위 테스트**를 만들었습니다.
알려진 몸통을 밀어넣고 1024바이트를 전부 뽑아 이미지를 재구성한 뒤, 레지스터
내용과 셀 단위로 대조하고 **켜진 칸을 전부 출력**하게 했습니다.

```
[FAIL] body cell (31,15) is dark
        lit cell (31,13)   ← 15가 아니라 13에 그려짐
        seg[0] = (31,15)   ← 레지스터는 맞음
```

y가 정확히 2칸(4픽셀) 어긋났고, 어긋난 것은 **마지막에 스캔되는 세그먼트(머리)**
뿐이었습니다. 두 사실을 합치니 마스크 시프트량이 6이어야 하는데 2가 된 것이
분명해졌습니다.

**원인** — Verilog의 폭 규칙입니다.

```verilog
wire [1:0] sub = ...;                       // 2비트
CELL_BITS << (sub << CELL_SH)               // sub=3, CELL_SH=1
```

`sub << CELL_SH` 의 **결과 폭은 왼쪽 피연산자의 폭**입니다. `sub` 이 2비트라
`3 << 1 = 6` 이 2비트로 잘려 `2` 가 됩니다. 그래서 마스크가 `0xC0` 대신 `0x0C`.

문법 오류도 아니고 경고도 없고, 세 세그먼트 중 둘은 우연히 맞았습니다
(sub이 0이나 1이면 잘리지 않으므로).

**수정** — 시프트량을 먼저 넓힙니다.

```verilog
wire [3:0] shamt = {2'b00, sub} << CELL_SH;
wire [7:0] cell_mask = CELL_BITS[7:0] << shamt;
```

**재발 방지** — 그 자리에 이유를 적은 주석을 남겼습니다. 그리고 단위 테스트를
`CELL_SH = 1/2/3` 세 설정 모두에 대해 돌립니다 — 폭 잘림은 파라미터에 따라
나타났다 사라졌다 하기 때문입니다.

## 4. 테두리가 반만 그려짐

**증상** — 캡처한 게임오버 프레임에서 상단 가로선은 없는데 오른쪽 세로벽은
있음. 벽 로직은 하나인데 결과가 갈렸습니다.

**어떻게 찾았나** — SSD1315 모델이 GDDRAM을 ASCII 아트로 덤프하게 해 뒀습니다.
정지 화면이 아니라 **패널이 실제로 받은 바이트**를 보는 것이라 이런 종류는
바로 눈에 띕니다.

**원인** — 프레임 한 장을 I2C로 밀어내는 데 약 25ms가 걸립니다. 테두리 깜빡임
신호가 자유 진동이라 프레임 중간에 토글됐고, 위쪽 페이지는 blink=1, 아래쪽은
blink=0으로 그려졌습니다. 화면 갱신이 순간이 아니라 **시간이 걸리는 과정**이라는
점을 놓친 것입니다.

**수정** — blink 위상을 프레임 시작에 래치합니다. 플립플롭 하나.

```verilog
always @(posedge clk)
    if (!rst_n)          blink <= 1'b1;
    else if (frame_done) blink <= blink_raw;
```

## 5. Zybo 조이스틱 핀 4개 오배정

**증상** — 아직 없었습니다. 보드에 올리기 **전에** 잡았습니다.

**어떻게 찾았나** — Vivado가 없는 환경이라 비트스트림을 만들 수 없으니, 대신
Digilent 공식 `Zybo-Z7-Master.xdc` 를 받아 제가 기억으로 적은 핀과 한 줄씩
대조했습니다.

**원인** — 마스터 XDC의 JC 배열이 이렇게 돼 있습니다.

```
jc[0]=V15 Sch=jc_p[1]     jc[1]=W15 Sch=jc_n[1]
jc[2]=T11 Sch=jc_p[2]     jc[3]=T10 Sch=jc_n[2]
```

JB/JC/JD는 **차동 Pmod**라 배열 인덱스가 `p[1], n[1], p[2], n[2] …` 순서이고,
p는 위쪽 줄(1~4번 핀), n은 아래쪽 줄(7~10번 핀)입니다. 즉 `jc[1]` 은 JC2가
아니라 **JC7** 입니다. 저는 인덱스 순서를 물리 핀 순서로 착각했고 5개 중 4개가
틀렸습니다.

**수정** — 전부 **Pmod JE** 로 옮겼습니다. JE는 standard Pmod라 배열 인덱스가
물리 핀 순서와 같고(`je[0] Sch=je[1]`), 마스터 XDC 주석에 핀 번호가 그대로
적혀 있어 추론할 것이 없습니다. 덤으로 200옴 직렬 보호 저항이 있어 손배선
모듈 앞에 두기에 더 안전하고, 필요한 신호가 정확히 8개라 딱 맞습니다.

**재발 방지** — `fpga/zybo_z7_20/check_xdc.py`. Vivado 없이 돌아가며, 포트마다
PACKAGE_PIN이 정확히 하나인지, 없는 포트를 제약하지 않았는지, 핀이 중복되지
않았는지, 각 핀이 마스터 XDC 기준으로 우리가 생각하는 보드 신호가 맞는지
확인합니다. 차동 Pmod 함정도 표에 주석으로 박아 뒀습니다.

## 6. 먹이가 벽 밑에 배치되어 안 보임

**유일하게 실제 보드에서 발견된 버그입니다.** 시뮬레이션이 놓쳤습니다.

**증상** — "먹이가 생성이 안 된 건지 테두리와 겹치는지 안 나타나는 경우가 생김".

**어떻게 찾았나** — 확률이 낮아 시뮬레이션으로 재현하기 나빴습니다. 대신 LFSR이
만들 수 있는 후보가 **유한**하다는 점을 이용했습니다. 11비트 LFSR의 주기는
2047이므로, 파이썬으로 전 주기를 돌려 범위 밖 후보가 몇 번 연속으로 나오는지
셌습니다.

```
in-range 확률                 = 71.1%
8번 연속 실패하는 지점         = 46 / 2047  (2.25%)
연속 실패 최장 구간            = 21
```

2.25%면 "가끔"과 정확히 맞습니다.

**원인** — 먹이 후보는 필드 안에 들어올 때까지 다시 뽑는데, 무한루프를 막는 탈출
카운터가 있었습니다. 그런데 레지스터를 줄이는 최적화에서 제가 `food_try` 를
6비트 → 3비트로 바꿨고, 그 결과 **탈출 임계값이 63 → 7**이 됐습니다. 그리고 그
경로는 후보를 범위 검사 없이 그대로 채택합니다.

```verilog
if (food_in_range || (food_try == 3'd7)) begin   // 7번 실패하면 범위 밖도 수용
```

범위 밖 = 벽이나 점수칸 → 벽 바이트 `0xFF` 가 덮어써서 **완전히 안 보임**.

면적을 줄이는 작업이 멀쩡하던 로직의 여유를 갉아먹은 경우입니다.

**수정** — 범위 검사에서 **탈출 경로를 아예 제거**했습니다. 무한루프가 아닌
근거는 위 전수 분석입니다 — 범위 밖은 최대 21번 연속이므로 최대 840ns 안에
빠져나옵니다. 게임 스텝이 100ms인 것을 생각하면 없는 시간입니다. 남은 탈출
카운터는 "뱀 몸통 위에 떨어진 경우"의 재추첨만 담당하며, 거기서는 포기해도
무해합니다(필드 안이고 몇 스텝 뒤 꼬리가 비켜남).

**시도했다가 버린 방법** — 후보를 범위 안으로 clamp 하는 방법을 먼저 넣었습니다.
유효성은 보장되지만 측정해 보니 **먹이의 18.7%가 첫 번째 열에 몰렸습니다.**
실제 플레이에서 티가 나므로 되돌렸습니다. 재추첨은 분포가 완전히 균등합니다
(모든 열이 정확히 56회).

**재발 방지** — `sim/tb_food.v`. 샘플링이 아니라 LFSR 2047개 상태를 **전수**
검사합니다: (1) 필드 밖 칸이 채택되는 일이 없는지 (2) 재추첨 루프가 유한한지
(3) 특정 열에 몰리지 않는지. 세 가지 셀 크기 모두에 대해 돌립니다.

## 7. 면적 추정이 두 번 틀림 (코드 버그 아님)

결론을 바꾼 오류라 같이 적습니다.

**첫 번째** — 표준셀 utilization을 60%로 **가정**했습니다. DK 안에 실제로 제작된
`pong_pt1` 의 라우팅 DEF가 들어 있는 것을 뒤늦게 발견해 재보니 **82.3%** 였습니다
(셀 0.5997mm² / DIEAREA 0.7284mm²).

**두 번째** — 그 뒤에도 숫자가 미심쩍어, 같은 `pong_pt1` RTL을 제 합성 흐름으로
돌려 실측과 비교했습니다.

| pong_pt1 | 셀 | 셀 면적 | 오차 |
|---|---|---|---|
| 실제 테이프아웃 | 1017 | 0.5997 mm² | — |
| `synth -flatten` + 기본 `abc` | 829 | 0.5058 mm² | **-16%** |
| qflow 자신의 스크립트 | 1061 | 0.6066 mm² | **+1.2%** |

기본 yosys 흐름은 실제보다 16% 작게 나옵니다. qflow는 delay 지향 매핑
(`map,-M,1,{D}`), abc 이후 flatten, 출력 버퍼 삽입을 합니다.

**수정** — `syn/area.py` 가 qflow 스크립트를 고정으로 쓰고, **실행할 때마다
pong_pt1 검증 결과를 먼저 출력**합니다. 낙관적인 숫자에 다시 속지 않도록.

**교훈** — 추정에는 반드시 기준점이 필요합니다. 마침 DK 안에 "정답"이 들어
있었는데 한참 뒤에야 썼습니다.

## 8. 패드 프레임 선택 오판 (코드 버그 아님)

PDK에 `MPW_PAD_84Pin_IO.mag` 가 있길래 면적이 부족하면 그걸 쓰면 된다고 문서에
적었습니다. 공고문을 실제로 읽어보니 **패키지 칩은 `MPW_PAD_28pin` 표준 배치만
가능**하고, 더 크게 설계하면 사전 협의 후 bare die만 제공됩니다. 즉 실질적으로
선택지가 아니었습니다.

**교훈** — 파일이 존재한다는 것과 그 경로가 열려 있다는 것은 다릅니다.
1차 자료(공고문)를 먼저 읽었어야 했습니다.

## 정리: 어떤 방법이 무엇을 잡았나

**격리 (#1)** — 전체 시스템에서 두 모듈만 남기고 신호 전이를 전부 찍는 것.
프로토콜 레벨 버그에는 이게 제일 빠릅니다. 파형 뷰어보다 로그가 나을 때가 많습니다.

**내부 상태와 출력을 대조 (#2, #3)** — "레지스터는 맞는데 그림이 틀리다"를 확인한
순간 탐색 범위가 절반으로 줄었습니다. 저장과 표시를 각각 독립적으로 확인할 수
있어야 합니다.

**지향적 단위 테스트 (#3)** — 시스템 시뮬 2분 vs 단위 시뮬 0.5초. 반복 속도가 곧
디버깅 속도입니다. 그리고 단위 테스트는 "틀렸다"가 아니라 **"어디가 어떻게
틀렸다"**를 알려주게 만들어야 합니다 — 켜진 칸을 전부 출력하게 한 것이
결정적이었습니다.

**최종 출력을 사람이 볼 수 있게 (#4)** — 패널이 실제로 받은 바이트를 ASCII
아트로 덤프한 것. 티어링처럼 시간이 얽힌 문제는 이렇게 봐야 보입니다.

**1차 자료 대조 (#5, #8)** — 기억으로 적은 핀 번호와 "PDK에 있으니 쓸 수 있겠지"
라는 추측. 둘 다 원본을 확인하니 바로 틀린 게 드러났습니다.

**유한하면 전수 검사 (#6)** — LFSR 주기가 2047이라 "칩이 만들 수 있는 모든 후보"가
유한합니다. 확률이 낮아 시뮬로 재현하기 나쁜 버그도, 상태 공간이 작으면 전수
검사가 샘플링보다 압도적으로 강합니다.

**추정에는 기준점을 (#7)** — 같은 도구로 정답이 알려진 케이스를 먼저 풀어보고
오차를 확인한 다음에 본 문제에 쓸 것.

### 그리고 하나 더

**#6은 최적화가 만든 버그입니다.** 면적을 줄이려고 카운터 폭을 6비트에서 3비트로
바꿨는데, 그 카운터는 단순한 카운터가 아니라 **정확성을 보장하는 여유(margin)**
였습니다. 폭을 줄이는 변경은 "값이 들어가는가"만 볼 게 아니라 **그 값이 무엇을
보장하고 있었는가**를 봐야 합니다.

그리고 이 버그는 시뮬레이션 19개 체크를 전부 통과했습니다. 발생 확률이 2%라 짧은
시나리오에서는 그냥 안 나옵니다. **보드에서만 나오는 버그가 있다**는 것과, 그래서
실제 하드웨어에 빨리 올려보는 것이 중요하다는 이야기입니다.
