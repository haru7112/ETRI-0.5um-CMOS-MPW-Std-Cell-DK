# 면적 리포트 (ETRI 0.5um, 실측)

> **정정 이력**: 첫 판에서 "84핀 프레임을 쓰면 된다"고 적었으나 이는 틀렸습니다.
> 2026년 3차 내 칩 제작 서비스 공고 기준으로 **패키지 칩은 `MPW_PAD_28pin`
> 표준 배치만 가능**하고, 그보다 크게 설계하면 사전 협의 후 **bare die만**
> 제공됩니다. 또 utilization을 60%로 가정했으나 실제 테이프아웃 결과는
> 82.3% 였습니다. 아래는 모두 실측으로 다시 계산한 값입니다.

## 0. 실측 — qflow P&R 완주 결과 (2026-09-04)

아래 1~4절은 합성 단계 추정치입니다. **place와 route를 끝까지 돌린 실제 값**이
나왔으므로 그것부터 적습니다.

```
make synthesize   에러 0
make place        성공
make route        Final: No failed routes!
make size         1422.600 x 1381.050 um  =  1.965 mm2
```

| | |
|---|---|
| 합성 직후 | 2421 cells / 329 FF |
| vlogFanout 후 | 2548 cells (버퍼 127개 추가) |
| 배치된 셀 면적 | 42,375 um x 36 um = **1.526 mm2** |
| **라우팅된 코어** | **1422.60 x 1381.05 um = 1.965 mm2** |
| 28핀 코어 창 | 1018 x 1018 um = 1.036 mm2 |
| **면적비** | **1.90배** |
| 한 변 | 가로 1.40배, 세로 1.36배 |

들어가려면 한 변을 각각 29% 줄여야 하고, 이는 **면적 47% 감축**입니다.

### 추정이 얼마나 맞았나

| | 값 | 3절 추정 대비 |
|---|---|---|
| 합성 셀 면적 | 1.435 mm2 | 1.445 mm2, **-0.7%** |
| 이용률 | 77.7% (`initial_density = 0.8` 설정) | 82.3% 가정 |
| 코어 | 1.965 mm2 | 1.756 mm2, **+12%** |

셀 면적 추정은 0.7% 안으로 맞았습니다. 코어가 12% 큰 이유는 두 가지입니다:
vlogFanout이 팬아웃 해소용 버퍼 127개를 넣어 셀이 6% 늘었고 (합성 stat에는
안 잡힙니다 - 그 단계 이후에 추가됩니다), 실제 달성 이용률이 가정한 82.3%가
아니라 77.7%였습니다. 3절 표의 배수는 전부 이만큼 낙관적으로 읽어야 합니다.

### 라우팅은 문제가 아닙니다

2메탈, `initial_density = 0.8`에서 실패 넷 0개로 완주했습니다.

```
stage1  실패 205        stage2  실패 0        stage3 2라운드  클린
```

밀도를 더 올려 코어를 줄이는 여지는 있지만, 킷 최고치인 95%를 가정해도
1.526 / 0.95 = 1.606 mm2 = 1.55배로 여전히 넘습니다. **밀도로는 해결되지
않습니다.**


### 0-2. 합성 레시피 — RTL 한 줄 안 고치고 13%

qflow가 쓰는 yosys 스크립트는 고정된 게 아닙니다. `project_vars.sh`에
`yosys_script`(기본 `synth -top ...`를 대체할 파일)와 `abc_script`(abc의
`-script` 인자) 두 훅이 있고, 이 프로젝트는 둘 다 씁니다.

| 레시피 | 셀 면적 | 논리 단수 | 최악 reg-to-reg |
|---|---|---|---|
| qflow 기본 (`synth`, `map,-M,1,{D}`) | 1.242 mm2 | 21 | 8.6 ns |
| `-flatten` 만 추가 | 1.153 mm2 | 18 | - |
| **채택: `-flatten` + `map,-a;mfs;amap`** | **1.075 mm2** | 31 | **10.6 ns** |
| 보수적 대안 `...;map;mfs;map` | 1.144 mm2 | 15 | 8.7 ns |

`-flatten`이 대부분을 차지합니다. 이 설계는 화면 기하를 파라미터로 내려보내고
블록 사이를 1비트 핸드셰이크로 잇기 때문에, 모듈 경계를 넘지 못하면 상수 폴딩이
막힙니다. 평탄화하면 플립플롭이 288 -> 284개로 줄고 조합 논리가 8% 빠집니다.
나머지는 `map,-a`(면적 우선 매핑, 기본은 지연 우선) + `mfs`(돈케어 재최적화) +
`amap`(면적 전용 2차 매핑)입니다.

대가는 논리 단수입니다. 21단 -> 31단. 다만 liberty 테이블을 따라 최악 경로를
실제로 걸어보면 8.6 ns -> 10.6 ns 로, 40 ns 주기 안에서 여전히 3.8배 여유입니다
(배선 기생은 뺀 값이므로 테이프아웃 전 `make sta`로 확인할 것).

검증: 이 레시피로 뽑은 게이트 넷리스트를 RTL과 나란히 220,000 클럭 돌려
모든 출력 비교, **불일치 0**.

주의 하나. `synth -flatten`은 워드 레벨 `$mux` 하나를 남기는데 `abc -liberty`가
이걸 건드리지 않아 매핑 안 된 셀로 배치기까지 갑니다. `yosys_hl.ys`의
`techmap` 한 줄이 그걸 막습니다.

### 0-4. RTL 축소 — 0.993 -> 0.928 mm2

합성 레시피로 1.242 -> 1.075를 얻은 뒤, RTL에서 다섯 가지를 더 줄였습니다.
전부 게임 규칙, 4x4 셀, 점수 표시, 칩이 OLED를 직접 구동하는 구조를 그대로 두고
한 것입니다.

| | 셀 면적 | 차이 |
|---|---|---|
| 합성 레시피만 적용 | 1.075 | |
| + 몸통 큐를 자유 회전으로 | 0.993 | -0.082 |
| + build_cnt 폭을 INIT_LEN 기준으로 | 0.983 | -0.010 |
| + oled_ctrl 카운터 폭 / 윈도우를 ROM 앞으로 | 0.968 | -0.015 |
| + 방향 버튼은 디바운스 없이 동기화만 | 0.948 | -0.020 |
| + pixel_gen 출력 레지스터 제거 | **0.928** | -0.020 |

**몸통 큐 (가장 큼).** 이 라이브러리에는 인에이블 달린 플립플롭이 없습니다
(DFFPOSX1과 DFFSR뿐). 그래서 값을 유지할 수 있는 레지스터는 전부 게이트로 만든
피드백 먹스를 물고, 두 가지로 쓰이는 레지스터는 먹스를 하나 더 뭅니다. 큐가
정확히 그랬습니다:

```
dq[i] <= move ? dq[i-1] : (scan_busy ? dq[i+1] : dq[i])
```

64비트 전부에 먹스 2단. 칩에서 가장 큰 조합 논리 덩어리였습니다.

이제 큐는 **매 클럭 무조건 도는 회전기**입니다. `dq[1] .. dq[MAXLEN-1]`에는
입력 논리가 아예 없고 (이웃에 직결), `dq[0]`만 먹스 하나를 답니다. 대신
위상 카운터를 두고 불변식을 하나 잡습니다:

```
위상 p 에서   dq[i] == seg[(i + p) mod MAXLEN]
```

그러면 두 동작이 회전 자체에서 떨어져 나옵니다.

* **스캔**: 위상 p에서 dq[0]은 곧 세그먼트 p입니다. 스캔은 큐가 들어가는 모드가
  아니라, 위상 0부터 한 바퀴 동안 dq[0]을 보는 것뿐입니다. **세그먼트 인덱스가
  곧 위상**이라 스캔 카운터가 사라졌습니다.
* **이동**: 링에서 맨 앞에 하나 끼우고 맨 뒤를 버리는 것은 한 칸 더 돌리는 것과
  같습니다. 회전은 어차피 돌고 있으니, 이동은 **위상 하나를 건너뛰는 것**이
  전부입니다. 위상 MAXLEN-2에서 dq[0]이 이웃 대신 새 방향을 받고 위상이 0으로
  점프합니다.

대가는 게이트가 아니라 지연입니다. 이동은 위상 MAXLEN-2를, 스캔은 위상 0을
기다리므로 각각 최대 MAXLEN-1 클럭. 게임 한 스텝이 208 ms, 패널 한 바이트가
32클럭이라 아무도 눈치채지 못합니다. 다만 호출자는 기다려야 하므로
`move_busy`가 생겼고, game_ctrl의 S_BUILD가 그걸 봅니다.

snake_body 0.402 -> 0.310 (-23%), game_ctrl은 대기 조건 때문에 +0.006.

**방향 버튼 디바운스 제거.** 방향은 레벨로, 그것도 208 ms에 한 번만 읽습니다.
game_ctrl은 버튼이 눌려 있을 때만 dir_nxt를 갱신하므로, 채터링이 잠깐 "떼임"
으로 튀어도 마지막으로 눌린 방향이 남습니다. 고칠 게 없으니 4개는 동기화
2단만 쓰고, 에지로 읽는 OK 하나만 필터를 유지합니다.

**pixel_gen 출력 레지스터.** busy가 내려간 뒤에는 다음 req까지 acc에 쓰는 게
없고, 다음 req는 oled_ctrl이 그 바이트를 SPI 시프터에 넘긴 뒤에만 옵니다.
이미 안정된 값을 8개 플롭에 또 복사하고 있었습니다.

### 0-5. 현재 위치

```
셀 면적            0.928 mm2   (1510 -> 1486 셀, 266 FF)
vlogFanout 후      0.986 mm2   (+6.3%, 실측 계수)
코어 @ density 0.85  1.160 mm2 = 창의 1.12배

코어 @ density 0.95  1.038 mm2 = 창의 1.00배

```

아침 기준(1.242, 정직한 값)에서 **-25%**. density 0.95면 창에 딱 맞고,
P&R이 실제로 완주했던 0.85로는 아직 12% 큽니다.

남은 카드:

* 프레임마다 보내는 주소 윈도우를 빼면 -0.032 (0.896). 대신 SCLK 한 비트가
  튀었을 때 스스로 복구하는 성질을 잃습니다. 측정해 뒀습니다.
* MAXLEN 32 -> 24 로 -0.03 정도. 뱀 최대 길이가 줄어듭니다.
* density를 0.90~0.95로 올리기. 2메탈에서 라우팅이 통과하는지는 돌려봐야 압니다.

### 0-3. score_bcd가 연결돼 있지 않았습니다

점수를 game_ctrl에서 빼서 몸통 길이로부터 계산하도록 바꾸면서, snake_top이
`score_bcd`를 만들어 놓고 pixel_gen에 **연결하지 않았습니다**. RTL 시뮬레이션은
뜬 입력을 z로 읽고 z도 폰트 디코더를 지나면 숫자가 되기 때문에 그림이 그럴듯해
보였고, tb_snake는 snake_top 쪽 wire만 봤기 때문에 통과했습니다. 게이트 넷리스트
에서는 `\u_pix.score_bcd`가 undriven으로 남고, RTL과 나란히 돌리면 38 ms - 숫자가
처음 바뀌는 프레임 - 에서 갈라집니다.

막는 장치 두 개를 넣었습니다.

* `make lint`가 `iverilog -Wall`로 돌고 경고가 하나라도 나오면 실패합니다.
  이 실수는 `dangling input port 10 (score_bcd) floating` 으로 잡힙니다.
* 패널 모델에 `box_pixels(page, x0, x1)`을 넣고, tb_snake가 점수 칸에 켜진
  픽셀 수를 같은 숫자를 먹인 별도 font_rom과 대조합니다. 글리프가 아니라
  **점수에서 유리까지 가는 경로**를 보는 검사입니다.

이 버그가 있는 동안 면적이 과소 보고됐습니다. 점수 경로가 실제로 구동되면
qflow 기본 레시피 기준 2013 -> 2078 셀, 1.210 -> 1.239 mm2 입니다.


## 1. 면적 예산 — 어디서 나온 숫자인가

### 1-1. 코어 창: 1018 x 1018 um

DK 안의 실제 테이프아웃 결과물
(`Projects/RTL/pong_pt1/ETRI050_MyChip_MPW/pong_pt1_MPW2025_STD-II.tar.gz`)의
chip_top 레이아웃을 직접 측정했습니다. (lambda = 0.30um, magic 내부 단위 = 0.01um)

| 레이어 | 범위 | 크기 |
|---|---|---|
| `pong_pt1_Pad.mag` (패드링) | 91.5 ~ 1808.5 um | 1717 x 1717 um |
| `pong_pt1_Pin_Route.mag` (핀 라우팅 링) | **441.0 ~ 1459.0 um** | **1018 x 1018 um** |

핀 라우팅 링 안쪽이 코어가 쓸 수 있는 전부입니다.
**1018 x 1018 um = 1.036 mm²**, 공고문의 "GPIO 사용시 설계 면적 ~1.0mm x 1.0mm"와
일치합니다.

### 1-2. Utilization: 82.3%

같은 테이프아웃의 라우팅 완료 DEF (`pong_pt1.def`)에서:

```
DIEAREA (0,-600) (86400,83700)   ->  864.0 x 843.0 um = 0.7284 mm2
COMPONENTS 2065  ->  실제 셀 1017개 + FILL 1048개
실제 셀 면적 합 (LEF SIZE 기준)  =  0.5997 mm2
utilisation = 0.5997 / 0.7284   =  82.3 %
```

qflow(graywolf `initial_density = 0.85` + qrouter, 3-metal)의 실제 달성치입니다.

### 1-3. 따라서 예산

```
코어 창      1.036 mm2
x 82.3%   =  0.853 mm2 의 표준셀
          =  약 1974 GE  (GE = NAND2X1 면적 432 um2 기준)
```

## 2. 측정 방법 — qflow 자신의 스크립트로

**중요**: 합성 스크립트에 따라 면적이 크게 달라집니다.

qflow 1.4.100이 etri050 타깃에 대해 직접 써 내는 `.ys` 스크립트를 그대로 씁니다
(`Projects/RTL/pong_pt1/pong_pt1/pong_pt1.ys` 에 실물이 있습니다).
delay 지향 매핑 `map,-M,1,{D}`, abc 이후 flatten, 출력 버퍼 삽입이 특징입니다.

이 스크립트가 맞는지 **실제 제작된 칩으로 검증**했습니다.

| pong_pt1 | 셀 | 셀 면적 |
|---|---|---|
| 실제 테이프아웃 (`pong_pt1.def`) | 1017 | 0.5997 mm² |
| qflow 스크립트 (여기 `area.py`) | 1061 | 0.6066 mm² (**+1.2%**) |
| 평범한 `synth -flatten` + 기본 `abc -liberty` | 829 | 0.5058 mm² (**-16%**) |

기본 yosys 흐름은 실제보다 16% 작게 나옵니다. 그래서 `syn/area.py` 는 qflow
스크립트를 쓰고, 실행할 때마다 위 검증을 먼저 출력합니다.
재현: `cd syn && python3 area.py`

## 4. 최적화 기록

| 항목 | 효과 |
|---|---|
| 코어 전체를 동기 리셋으로 | `DFFSR`(72x36um) 304개 → 0개. 3.09 → 2.77 mm² |
| **몸통을 좌표 큐 → 방향 큐로** | 좌표 11bit x 48 → 방향 2bit x 48. snake_body 3331 → 1078 GE |
| pixel_gen의 벽/먹이 마스크 공유 | 픽셀 행 8개 비교기 → 상수 마스크 + 비교기 1개 |
| **위치 연산을 snake_body로 이동** | game_ctrl의 11bit 레지스터 2개와 먹스 트리 제거. 998 → 552 GE |
| oled_ctrl 중복 레지스터 제거 | `pix_x`/`pix_page`/`i2c_din` → 조합 논리, 윈도우 명령을 init에 통합 |
| debounce 3샘플 → 2샘플, lfsr16 → lfsr11 | FF 21개 |
| **글자 제거, 좌측 점수 레이아웃** | 알파벳 14자 + 메시지 배치 먹스 4종 제거. pixel_gen 585 → 352 GE |

**누적: 기본 yosys 흐름 기준 2.769 → 1.289 mm² (-53%).** 기능 손실은 텍스트 메시지뿐이고, 그 자리는
테두리 깜빡임이 대신합니다. 19개 시스템 체크 + CELL_SH 1/2/3 렌더러 단위검증
전부 통과.

## 5. 왜 더 못 줄이는가

ablation으로 측정한 결과, 개별 게임 기능은 전부 작습니다.

| 제거 대상 | 절감 |
|---|---|
| 점수 BCD 3자리 | 39 GE |
| 속도 테이블 → 고정 200ms | 64 GE |
| 먹이 범위 검사 | 8 GE |
| 벽 판정 | 43 GE |
| init ROM 26바이트 → 상수 | 114 GE |

면적은 게임 규칙이 아니라 **"폭 넓은 레지스터 × 여러 FSM 상태"의 next-state
먹스 트리**에 있습니다. 그래서 효과가 컸던 최적화는 전부 *레지스터를 없앤*
것들이었습니다.

남아 있는, 아직 적용하지 않은 항목과 예상 절감:

| 항목 | 절감 | 대가 |
|---|---|---|
| I2C → SPI | 약 270 GE (0.12 mm²) | 7핀 SSD1315 모듈 필요, 핀 3개 추가 |
| 방향 큐를 매 클럭 자유 회전 (3:1 먹스 → 2:1) | 약 86 GE | 위상 추적 로직, 전력 증가 |
| debounce를 2단 동기화 + OK 엣지만으로 | 약 95 GE | 방향 입력의 바운스 필터 없음 (틱 간격이 200ms라 무해) |
| init ROM을 필수 11바이트로 | 약 50 GE | RES# 핀에 의존 (전원인가 기본값 사용) |

전부 적용하면 4x4/MAXLEN 32 기준 약 1.27 mm² 셀 → **1.55 mm² 코어 (1.49배)**.
8x8 그리드 + MAXLEN 16까지 내리면 약 1.35 mm² 코어(1.30배)로, 여전히 넘습니다.

## 6. 결론

**현 구조로는 28핀 패키지 칩(코어 1.036 mm²)에 들어가지 않습니다.**
P&R을 끝까지 돌린 실측값이 **1.965 mm², 1.90배**입니다 (0절). 합성 단계 추정
1.69배는 낙관적이었고, 실제로는 면적을 **47% 줄여야** 합니다.

기능은 완전히 검증된 상태입니다 - 게이트 넷리스트와 RTL이 3,950만 클럭
(리셋, 패널 초기화, 프레임 렌더링, 게임 플레이, 먹이 배치 포함) 동안 출력
불일치 0, 라우팅 실패 넷 0. 들어가지 않는다는 것만이 유일한 문제입니다.

선택지:

1. **Bare die로 제작** (사전 협의, 패키지 없음). 표준 1.9x1.9mm 다이 안에 커스텀
   패드를 배치하면 4x4 px / MAXLEN 24 설정(코어 1.656 mm² → 한 변 1.29mm,
   패드 깊이 250um x 2 = 0.5mm, scribe 0.12mm → 1.91mm)이 거의 맞습니다.
   MAXLEN 16이면 1.87mm 로 여유가 생깁니다.
   단 본딩(COB)을 직접 해야 하므로 동작 확인이 어렵습니다.
2. **남은 최적화 + 그리드 축소.** 1.30배까지는 계산이 서지만 그 아래는 구조를
   바꿔야 합니다.
3. **다음 차수를 목표로.** 접수 마감은 2026-09-07 입니다.

어느 쪽이든 `cd ETRI050 && make synthesize` 로 진짜 숫자를 먼저 확인하는 것이
좋습니다. `make size` 가 라우팅된 코어의 실제 크기를 알려줍니다.
